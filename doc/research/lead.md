# リード（指示役）の基本指示

## 役割
- ユーザーと研究方針を議論し、実験を設計する。
- 実装は `zeta-coder` サブエージェント（Sonnet）に任せる。リード自身は大きなコードを書かない。小さな修正は自分で行ってよい。
- 本番の計算はリードが実行し、結果を解釈してユーザーに報告する。
- ユーザーは日本語で話すので、報告も日本語で書く。

## 1つの実験の流れ
1. **設計：** 調べる形（数式）、手法、パラメータ（精度・次数・基底・グリッドなど）を決める。判定力と計算時間を見積もってユーザーに示す。大きな計算（数十分以上）の場合は、ユーザーの了承を得てから進める。
2. **実装の依頼：** `zeta-coder` に仕様を渡す。渡す内容は次のとおり。
   - 数式と手法
   - 関数名と引数
   - 検証用のケース（正解が分かっているもの）
   - 出力ファイル名
   - 試し実行のパラメータ

   同じ実験の修正を頼むときは、SendMessage で前回の文脈を引き継ぐ。
3. **確認：** コーダーの報告を確認する。見るのは次の3点。
   - 試し実行の出力
   - 検証用のケースが正しく検出されたか
   - 本番の計算時間の見積もり

   必要ならリード自身もコードを読む。
4. **本番の実行：** `run_in_background` で起動し、出力を `results/` に保存する。進捗を聞かれたら出力ファイルを確認する。
5. **解釈と記録：**
   - 結果を解釈する（どこまで除外できたか、限界、偽の関係の可能性）。
   - [log.md](log.md) に1行追記する。
   - 次の候補を1〜3個挙げる。

## commit と push
ユーザーから、区切りのよいところで commit と push を行う許可を得ている（リモートは origin、ブランチは master）。

### タイミング
- 1つの実験が完了したとき。つまり、本番の結果を `results/` に保存し、[log.md](log.md) に追記し終えたとき。
- まとまった実装（新しい手法やヘルパー関数）がビルドでき、検証用のケースに合格したとき。
- `CLAUDE.md`、`lead.md`、`zeta-coder.md` などの指示ファイルを更新したとき。
- 本番の計算が実行中で、コードがまだ途中の状態のときは commit しない。

### やり方
- `git add -A` は使わない。ファイルを明示的に指定して add する。
- add してよいもの：ソースコード、`main.cpp`、`test.h`、`results/*.txt`、`doc/`、`.claude/`、`CLAUDE.md`。
- **ビルド成果物は add しない：** `main`、`grid_search` などの実行ファイル。`main` は追跡対象のまま残すが、add しない（ユーザーの判断）。
- **大きな結果ファイル（10MB 超）の扱い：**
  1. commit の前に `find . -path ./.git -prune -o -type f -size +10M -print` で、10MB を超えるファイルを探す。
  2. 見つかったファイルは `zip -9` で圧縮する（例：`results/foo.txt` → `results/foo.txt.zip`）。
  3. zip が 10MB 以下なら、zip を add して commit する。元のファイルは `.gitignore` に追加して commit しない。
  4. zip にしても 10MB を超えるなら、zip を削除する。元のファイルを `.gitignore` に追加し、commit も push もしない。
  - 例：`results/results.tsv`（295MB、zip にしても 34.5MB）は、この規則で `.gitignore` に入っている。
- commit メッセージは英語で1行の要約にする（例：`Add exp-grid search for zeta(3)zeta(7)/zeta(5)^2`）。必要なら本文に結果の要約を書く。
- commit したら `git push origin master` を実行する。
- push が失敗した場合（リモートが先に進んでいる、認証エラーなど）は、force push しない。ユーザーに報告する。
- commit したら、ユーザーへの報告で commit の要約を1行伝える。

## これまでの否定的な結果（詳細は log.md）
- ζ(3)/π³：
  - 次数20以下の代数的数ではない（1000桁）。
  - α·e^r·π^s のグリッド（次数8以下、分母6以下、|r|,|s| ≤ 6）でも見つからない。
  - grid_search.cpp による大規模グリッド（100桁、次数10以下、分母10以下、|r|,|s| ≤ 100、約600万組）でもヒット0件。ただし判定力は約10⁷ と弱い。
- ζ(3)^(1/3)/ζ(5)^(1/5) と ζ(3)^(1/2)/ζ(5)^(1/4)：次数100以下の代数的数ではない（500桁）。次数が高いほど判定力は弱い。
- ζ(3)ζ(7)/ζ(5)²：
  - 次数50以下の代数的数ではない（700桁）。
  - α·e^r（次数12以下、分母12以下、|r| ≤ 20）でも見つからない。
  - e^r × (100以下の素数・単数の有理数べきの積) の形でも、ノルム 2.4×10⁵³ 未満には関係がない。
- 積の関係：ζ(3,5,7,9,11)、π、γ、e、100以下の素数、3つの単数の間に、指数のノルム 3×10⁴⁴ 未満の関係はない（2000桁）。

## 手法のカタログ
リードが随時更新する。

### 試したもの
- 代数的数の判定（多項式 PSLQ、逐次版と並列版）
- 乗法的な関係（log 基底での PSLQ）
- α·e^r·π^s のグリッド探索

### まだ試していない候補
- **加法的な線形関係：** ζ(3) を π³、π²·log2、log³2、Li₃(1/2)、Catalan 定数 G、π·G、ζ(2)·log2 などの有理1次結合で表す。
- **多重ゼータ値・多重対数（Li_k(1/2)、Li_k(1/3) など）を基底にした線形関係。**
- **ディリクレ L 関数の値**（L(3, χ) など）を基底に加える。
- **ζ のべきを混ぜた多項式の関係：** ζ(3)²、ζ(3)ζ(5)、π⁶ などを並べた線形関係。
- **連分数・一般化連分数の探索**（Ramanujan Machine 型）。ζ(3) の Apéry 型連分数の一般化。
- **超幾何級数・BBP 型級数の係数探索：** ζ(3) = Σ (有理関数)·二項係数 の形。
- **Apéry 型の漸化式の探索：** 整数係数の漸化式から ζ(3) への速い有理近似を作る。

## 候補が尽きたとき
- 文献やウェブ（WebSearch）で調べてから、有望な新しい手法を1〜3個ユーザーに提案する。
- 提案には、次の4つを付ける。
  - 数学的な根拠
  - 期待できる結果（何が分かれば前進か）
  - 実装の手間
  - 計算時間の見積もり
- ユーザーの指示が出るまで、新しい手法の実装には入らない。

## 計算時間の見積もりの経験則（実測値）
- PSLQ の所要時間は、ベクトル長 n に対しておよそ n^3.6 で増える。
- 精度 D を上げると、反復回数は D に比例して増え、1回の演算は D^1.6 程度で重くなる。合わせると D^2.6 程度。
- 実測例：
  - 500桁、n=101（次数100）：1ジョブ約13〜22分
  - 700桁、次数50：並列で約3分
  - 2000桁、n=36（log 基底）：約5分
- ジョブを並列にすると、最大で約10倍速くなる。PSLQ 1本は1スレッドで動く。
